# B02 — Replace sessionStorage-only intro gating with deterministic native-process lifecycle ownership

Current user evidence:

- published native app opened directly to the UI;
- startup video did not appear.

The existing frontend-only `sessionStorage` guard is therefore not accepted as the authoritative lifecycle mechanism.

Required production behavior:

- cold native launch => video plays exactly once;
- SPA navigation => no replay;
- project selection => no replay;
- minimize/restore => no replay;
- Settings -> Restart H!veAI -> confirmed native restart => video plays exactly once again;
- app remains mounted behind overlay;
- `hiveai_frontend_ready` remains independent of video completion;
- browser preview does not try to run native intro playback;
- media error/failsafe leaves app usable;
- no browser, external media player, terminal, or second Tauri window.

## Required lifecycle design

Use a deterministic **native-process-scoped claim** rather than relying on WebView `sessionStorage` semantics.

Preferred design:

1. Add a tiny Rust application state for startup-intro ownership, initialized fresh for each native Tauri process.
2. Expose a dedicated command, for example:

   `hiveai_startup_intro_claim`

3. The first successful claim in a native process returns `true`.
4. Subsequent claims in the same native process return `false`.
5. A real `app.request_restart()` starts a new native process/lifecycle, so the state resets naturally and the first claim returns `true` again.
6. The frontend renders/plays the intro only when the native claim returns `true`.

A simple process-local `AtomicBool`, `Mutex<bool>`, or equivalent bounded state is acceptable.

Do not persist this claim to SQLite, filesystem, registry, localStorage, or sessionStorage.

Do not create a general lifecycle subsystem.

Do not modify the existing restart command semantics except for the minimum wiring necessary to ensure the new process-local intro state is registered normally on each process startup.

## Native command governance

Follow existing H!veAI Tauri command patterns:

- command must be explicitly registered;
- add the narrow permission/capability entry required by the current ACL model;
- no broad allow-all capability;
- no public bypass/test-only runtime flag.

## Frontend behavior

`StartupIntro` should:

- detect native environment using the established Tauri boundary;
- asynchronously claim intro ownership from native state;
- show a safe black/deep-navy initial overlay while the claim resolves, so the app does not flash before the video decision;
- if claim = true, play bundled `opening-video.mp4`;
- if claim = false, dismiss immediately without playback;
- if claim command errors unexpectedly, fail open to usable app rather than trap the user;
- preserve natural `ended` handling, 280 ms-ish premium fade, and bounded media failsafe;
- keep the underlying `<App />` mounted immediately;
- keep `hiveai_frontend_ready` independent.

Remove `hiveai.startup-intro.played` sessionStorage as the authoritative gating mechanism. If any frontend in-memory guard remains, it must only prevent duplicate rendering during the same mounted frontend tree and must not decide native lifecycle truth.
